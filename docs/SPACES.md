# Личные и общие пространства

Каждый аккаунт получает личное пространство. Доступ к нему есть только у этого аккаунта. Общее пространство — отдельный набор задач, проектов, календарей и настроек; создание общего пространства не переносит и не раскрывает личные данные.

## Как пригласить друга

1. Войдите в существующий аккаунт: логин `owner`, прежний пароль. Старые формы входа без логина продолжают работать.
2. Откройте «Управление» рядом с переключателем пространства, введите название и создайте общее пространство.
3. Нажмите «Пригласить по ссылке» и скопируйте показанную ссылку. Полная ссылка отображается только при создании; после закрытия её можно заменить новым приглашением. Отправка ссылки выполняется пользователем.
4. Друг открывает ссылку, задаёт логин, имя и пароль длиной от 12 символов. Существующий пользователь может войти и принять приглашение своим аккаунтом.
5. Переключайтесь между личным и общим пространствами. При незавершённом сохранении переключение временно недоступно.

Приглашение одноразовое, действует семь дней и может быть отозвано владельцем до использования. По ссылке её получатель получает доступ ко всему общему пространству. Владелец управляет приглашениями и участниками; участники могут редактировать общее содержимое. Личное пространство нельзя превратить в общее или открыть приглашением. Удаление участника прекращает его доступ и удаляет выпущенные им токены этого пространства. Повторное приглашение не восстанавливает старые токены.

Список участников доступен всем участникам. В истории новых действий отображается имя автора. Общие изменения появляются при очередном обновлении состояния (обычно в течение 15 секунд у активной вкладки) или при возвращении фокуса. Одновременные изменения используют существующие проверки ревизий и повторное применение действий.

## Граница приватности

Проверка членства выполняется на сервере для REST, MCP, календарей и токенов. Заголовок с идентификатором пространства не предоставляет доступ сам по себе. Приватность действует между аккаунтами приложения. Администратор сервера и резервных копий имеет доступ к сохранённым данным; сквозное шифрование содержимого не реализовано.

Календарь, подключённый внутри общего пространства, показывает события всем его участникам. URL подписок и учётные данные CalDAV остаются на сервере и не возвращаются через состояние или MCP. Подключение личного календаря в личном пространстве не открывает его участникам общих пространств.

## Хранение и API

- `users` хранит отдельные аккаунты и хеши паролей. Новые сессии содержат подписанный идентификатор пользователя. Старые v1-сессии действуют только для исходного аккаунта.
- `spaces` и `space_members` отделяют пространство от пользователя. `workspaces.owner_id` сохранён как физический ключ пространства: существующие ID, шифрование CalDAV, ревизии и квитанции действий остаются прежними.
- Браузер передаёт `X-Life-Space` и `X-Life-Account`. Первый выбирает пространство после проверки членства; второй не позволяет вкладке отправить старую очередь от имени другого аккаунта после смены сессии.
- Без `X-Life-Space` браузерный API использует личное пространство. Токен всегда привязан к одному пространству и своему создателю; заголовок не может переназначить его.
- Владелец пространства видит и отзывает все его токены. Участник управляет только собственными. Проверка членства и действительности токена повторяется в транзакции записи.
- Черновики очереди остаются в `sessionStorage` своего аккаунта и пространства. Для прежнего личного пространства сохранён старый ключ. Потеря доступа скрывает состояние и блокирует изменения, сохраняя черновики для возможного восстановления доступа; они не переносятся в другое пространство.
- Фоновый обработчик событий обходит все сохранённые пространства с отдельной проверкой ревизии для каждого.

`GET /api/spaces` возвращает доступные пространства. `GET /api/spaces?space=ID` — участников и, для владельца, неиспользованные приглашения без исходных токенов. `POST /api/spaces` поддерживает `create`, `invite`, `accept`, `removeMember`, `revokeInvite`. `POST /api/session/register` требует действующее приглашение. Открытой регистрации нет.

## Обновление и восстановление

Миграция `0004_accounts_spaces.sql` применяется обычным механизмом запуска SQLite. Она создаёт личные пространства для существующих владельцев и связывает старые токены с их пользователями. Пароль исходного аккаунта берётся из прежней конфигурации при первом заполнении записи аккаунта; последующие запросы не перезаписывают хеш.

Перед выпуском требуется штатная согласованная резервная копия SQLite и сохранение действующих ключей сессий и CalDAV. Восстанавливать нужно полную базу вместе с конфигурацией: в ней находятся все аккаунты, участники и приглашения. Для отката к версии без пространств следует восстановить резервную копию до обновления; старый код не учитывает новую модель доступа.

Старый формат переноса `life-os-migration-v1` предназначен только для исходного единственного личного аккаунта. Экспорт блокируется при наличии нескольких аккаунтов или общих пространств, чтобы не создавать неполную копию. Импорт старого снимка создаёт одну личную запись аккаунта и сохраняет исходные ключи данных. Для системы с общими пространствами используется полная резервная копия SQLite.

Первый выпуск не включает самостоятельное восстановление пароля, передачу владения пространством, перенос задач между пространствами, мгновенную совместную редактуру или общий вид нескольких пространств. Новые аккаунты входят по логину и паролю; текущая поддержка Sites остаётся механизмом совместимости для исходного аккаунта.
